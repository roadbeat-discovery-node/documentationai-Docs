<Update label="2026-11-09" description="v1.5.1" tags={["security","bugfix"]}>
  ## Privacy, rate limiting and "more like this"

  **Publisher contact data stays private**

  - `GET /api/v1/publishers` and `GET /api/v1/publishers/:id` now return an **allowlist of public fields** — the contact person and e-mail (`contactName`, `contactEmail`) are no longer part of public responses. New database columns stay private until they are added to the list on purpose.
  - New admin endpoint **`GET /api/v1/publishers/:id/contact`** (`X-Admin-Key`) for the node operator.
  - The transparency website's publisher list (`GET /api/web/v1/publishers`) only sorts by an allowlist of public columns; unknown sort fields fall back to `createdAt` instead of failing with `500`.

  **Rate limiting per client behind the reverse proxy**

  - New variable **`TRUST_PROXY`** (default `1` = one reverse proxy). The global limit of 120 requests/min is now counted per real client address taken from `X-Forwarded-For` across trusted hops — previously all clients behind Caddy shared one bucket.
  - `TRUST_PROXY=true` logs a warning; an invalid value stops the API at startup. See [Reverse proxy and client IP](/deployment/configuration#reverse-proxy-and-client-ip).

  **"More like this" without embeddings**

  - `POST /api/v1/embedding/similar/:teaserId` falls back to Elasticsearch `more_like_this` (headline, description, categories, topics, tags) when no embeddings are available or the vector search fails. The response's new `method` field says which (`vector` / `more_like_this`).
  - Finds the source teaser by `teaser_id` or document `_id` (the old lookup field was not mapped), excludes expired teasers and switched-off publishers, limits `limit` to 1–50, and only accepts `roadbeat-content-*` indices.

  See [Semantic Search](/features/semantic-search#similar-content-more-like-this) and [Publisher Management](/features/publishers#public-publisher-record).
</Update>

<Update label="2026-11-08" description="v1.5.0" tags={["feature","bugfix"]}>
  ## Publisher "About" text, search fixes

  - **About text per language** — `PUT /api/v1/publishers/me/description` sets `{ "<language>": "<plain text>" }` (max. 2,000 characters each); the text is part of the public publisher record as `description`.
  - **Fix: search cache key** — the cache key is now a SHA-256 of the full request. Before, requests that differed only in sort direction or page could get the cached answer of another request for 30 s ("Title Z→A" showed A→Z, page 2 showed page 1).
  - **Fix: Publishers facet** — the `publisher.name` filter (sent when a bucket of the Publishers facet is checked) was ignored and returned every publisher's content.

  **Database migration:** `description` (JSONB) on `publishers` — run `prisma migrate deploy` when updating.

  See [Publisher Self-Service](/features/publisher-self-service#about-text) and [Publisher filters](/features/search#publisher-filters).
</Update>

<Update label="2026-11-07" description="v1.4.0" tags={["feature","bugfix"]}>
  ## Content Pod publishers and publisher self-service

  **Content Pod verification** — publishers without a domain of their own verify through their Content Pod:

  - `POST /api/v1/publishers/:id/verify-pod` checks `/.well-known/roadbeat-publisher.json` (publisher id + public key) and marks the publisher `pod_verified` (verified badge, rate limits of unverified publishers).
  - `POST /api/v1/publishers/:id/pod-sync` applies what the pod declares: `suspended` switches the publisher off, `active` on, `deleted` removes the publisher **and all its teasers**; a new public key is taken over with a proof of possession, and a new API key is returned once.
  - Only hosts in the new variables `POD_VERIFY_HOSTS` (default `.pods.roadbeat.net`, https) and `POD_VERIFY_INSECURE_HOSTS` (http, development only) are fetched.

  **Publisher self-service** (with `X-Publisher-Key`):

  - `GET /api/v1/publishers/me` — whom the key belongs to.
  - `PUT /api/v1/publishers/me/public-key` — replace the Ed25519 key, signed proof with the new key required.
  - `POST /api/v1/publishers/me/deactivate` / `reactivate` — switch the publisher off and on.
  - `PUT /api/v1/publishers/me/avatar` — optional publisher picture, opt-in, Content Pod publishers only and only a file inside their own pod.

  **Switched-off publishers are offline** — teasers of publishers deactivated by their owner or suspended by an admin are hidden from search, goal search, suggestions, teaser lookups and similar content; they stay in the index and return instantly on reactivation. Deactivated publishers get `403` on ingest.

  **Search**

  - **Free text within goals** — `POST /api/v1/search/by-goals` accepts `query.text`: hits must match the text and at least one content query.
  - **Fix: muted publishers** — the `publisher.id_exclude` filter is now honoured in `/search` and `/search/by-goals`.
  - **Fix: directory search** — `GET /api/v1/publishers?q=` now searches name and domain (it was ignored).

  **Database migrations:** `owner_deactivated` (boolean) and `avatar_url` on `publishers` — run `prisma migrate deploy` when updating.

  See [Content Pod Publishers](/features/content-pod-publishers) and [Publisher Self-Service](/features/publisher-self-service).
</Update>

<Update label="2026-03-16" description="v1.2.1" tags={["bugfix","feature"]}>
  ## Boolean filter coercion fix

  **Query builder**

  - **`coerceBooleanValue()`** — new helper in `QueryBuilderService` that converts string representations of booleans (`"1"`, `"0"`, `"true"`, `"false"`) to actual ES boolean values (`true`, `false`) before building `terms` or `term` queries on `type_filters.` fields

  - `applyTypeFilters() `**updated** — all `type_filters` filter values are now passed through `coerceBooleanValue()`, ensuring that frontend filter values (which use `"1"`/`"0"` strings) correctly match ES documents where boolean fields are stored as native boolean type

  - **Backwards compatible** — non-boolean string values (e.g., `"analysis"`, `"free"`) pass through unchanged
</Update>

<Update label="2026-03-16" description="v1.2.0" tags={["feature"]}>
  ## Schema-driven content-type-specific filters

  **Dynamic facet engine**

  - **`DynamicFacetService`** — new service that reads `x-filter` annotations from content type metadata schemas (fetched from Schema Registry, cached 10 min) and dynamically builds `FacetDefinition[]` for any content type — zero hard-coded per-type configuration

  - `type_filters `**ES sub-object** — new `dynamic: true` sub-object in the ES index template with `dynamic_templates` mapping strings as `keyword` and date-suffixed fields as `date` — allows arbitrary filter fields without template changes

  - **Deleted** `CONTENT_TYPE_FACETS` — removed the hard-coded per-type facet map from `facet-config.ts`, replaced entirely by schema-driven definitions

  **Enhanced facet metadata**

  - `FacetDefinition `**interface** expanded with `labels` (multilingual), `ui_hint` (widget type), `unit` (range label), `priority` (display order), `content_type_specific` (boolean flag)

  - `FacetDto `**response** now includes `content_type_specific`, `ui_hint`, `unit`, `labels`, `priority` fields for type-specific facets

  - **UI hint auto-inference** — when not explicitly set in the schema, `ui_hint` is inferred from enum count: ≤6 → `chips`, 7-15 → `checkboxes`, >15 → `searchable_checkboxes`

  **Query builder**

  - **`applyTypeFilters()`** — new filter method handling `type_filters` keys with support for terms (string/array), boolean, and range (`min`/`max` or `gte`/`lte`) filters

  - **type\_filters pass-through** added to `mapGoalCatalogFilters()`, `buildGoalBatchQuery()`, and `buildRandomQuery()` global filter paths

  **Aggregation pipeline**

  - **`buildAggsFromFacetDefs()`** — new method in `SearchService` that builds ES aggregation clauses from `FacetDefinition[]` (terms, date\_histogram, stats for ranges)

  - Both `search()` and `searchByGoalBatch()` now use facet-definition-driven aggregations instead of hard-coded defaults
</Update>

<Update label="2026-03-14" description="v1.1.0" tags={["feature"]}>
  ## Batched goal search & random mode

  **New endpoint:** `POST /api/v1/search/by-goals`\*\*

  - Accepts an array of pre-resolved `content_queries` from one or many user goals and builds a single Elasticsearch `bool.should` **query** — enabling 150+ content\_queries to execute in one ES request instead of 150 separate ones

  - Each content\_query becomes a `should` clause with content\_type filter, classification filters, and relevance-based boost weighting (high=1.5, medium=1.0, low=0.5)

  - Supports **named queries** for goal attribution — each clause carries `_name: "goal:{goalId}:cq:{index}"` so ES returns `matched_queries` identifying which goals matched each result

  - Global user filters (date range, language, publisher, geographic) applied at the top-level `filter` clause across all goal queries

  - Uses wildcard index `roadbeat-content-*` to avoid `index_not_found_exception` when some content types have no indexed content yet

  **Random / Surprise mode**

  - New `random` flag on the batch endpoint triggers `function_score` with `random_score` for serendipitous content discovery

  - Session-stable pagination via `random_seed` — same seed produces same ordering within a session

  - Optional light bias from user's goal categories (low boost 0.3) so random results lean slightly toward the user's interests

  **Goal catalog filter mapping**

  - `mapGoalCatalogFilters()` translates goal catalog filter paths to Elasticsearch classification paths: `category.tags` → `classification.tags`, `category.categories` → `classification.categories`, `category.primary` → `classification.primary_category`, `category.topics` → `classification.topics`

  - DN-native paths (`classification.*`, `temporal.*`, `access.*`, `publisher.*`, `geographic.*`, `metadata.*`) passed through directly

  - Unknown content-type-specific keys (e.g. `event_type`, `mood`, `industry`) are silently ignored since the teaser generator does not populate them in the index
</Update>

<Update label="2026-03-10" description="v1.0.0" tags={["feature"]}>
  ## Initial Release

  The roadbeat Discovery Node v1.0.0 includes a complete distributed search and content discovery server with the following capabilities:

  **Search & Discovery**

  - Full-text BM25 search with German and English analyzers

  - Hybrid search (BM25 + kNN vector similarity) via OpenAI embeddings

  - Goal-based search with filterset template parameter substitution

  - Autocomplete suggestions with phrase prefix and fuzzy matching

  - 11 global facets + 4 content-type-specific facet sets

  **Content Ingest**

  - Teaser publish, update, delete, and batch operations (up to 100)

  - Ed25519 signature verification for content integrity

  - Automatic embedding generation at ingest time

  - Per-content-type Elasticsearch indices

  **Publisher Management**

  - Publisher registration with one-time API key

  - DNS TXT record domain verification

  - 4-tier verification levels with tiered rate limits

  - Admin operations: key rotation, suspension, updates

  **Node Federation**

  - Peer node directory with heartbeat protocol

  - Stale node detection (5-minute timeout)

  - Node registration, update, and removal

  **Infrastructure**

  - Elasticsearch 8.11.4 with auto-created index templates

  - Redis caching for search results (30s), suggestions (60s), directory (5min)

  - NATS JetStream event streaming for teaser lifecycle events

  - PostgreSQL via Prisma ORM for metadata storage

  **Transparency Website**

  - Next.js 14 public dashboard with 24 EU language support

  - Statistics page with Recharts visualizations

  - Real-time health monitoring (10s polling)

  - Content type browser, publisher directory

  - Dynamic legal pages (imprint, privacy, terms)

  **Security**

  - Helmet HTTP security headers

  - Global rate limiting (120 req/min/IP)

  - Per-publisher Redis sliding window rate limiter

  - SHA-256 hashed API keys with constant-time comparison

  - Input validation with class-validator (whitelist + forbidNonWhitelisted)

  - Configurable CORS

  **DevOps**

  - Multi-stage Docker builds for API and Web

  - Production Docker Compose stack with Caddy reverse proxy

  - GitHub Actions CI pipeline (lint, build, Docker)

  - Environment validation with startup checks
</Update>
